1 Цель и описание сценария
Цель работы - исследовать на учебном стенде AMPIRE последствия SQL-инъекции в веб-приложении магазина, проверить доступ к файлам сервера средствами СУБД и проанализировать попытку выхода из Docker-контейнера.
Сценарий включает поиск сервисов, проверку параметра поиска товаров, извлечение хеша первого флага, его восстановление, прямое подключение к MariaDB и чтение второго флага. Заключительный этап посвящён использованию cgroup и release_agent.
2 Среда и инструменты
- Платформа: AMPIRE, тренировка «ЛР2 [НБИ-01-23 Delta] v0».
- Дата выполнения по скриншотам: 7 октября 2026 года.
- Рабочая среда: Kali Linux, пользователь reduser2.
- Исследуемая сеть стенда: 195.239.174.0/24.
- Веб-приложение и СУБД: 195.239.174.35, TCP 80 и 3306.
- Инструменты: Nmap, Firefox, sqlmap, Hashcat, клиент mysql, оболочка Linux.
Названия заданий сохранены из AMPIRE. Фактически сервер СУБД идентифицирован как MariaDB 11.5.2.
3 Ход выполнения работы
3.1 Сканирование учебной сети
Работа началась с поиска доступных узлов и сервисов в сети стенда. В терминале Kali Linux запущен Nmap с определением версий сервисов и стандартными сценариями проверки. На первом снимке сканирование ещё продолжается. В итоговом выводе на последующих снимках указаны 256 проверенных адресов и 6 доступных узлов.
nmap -sV -sC 195.239.174.0/24
Сформирована основа для выбора цели. На узле 195.239.174.35 обнаружены HTTP на порту 80 и MariaDB на порту 3306.

Рисунок 1 - Сканирование учебной сети
3.2 Веб-интерфейс магазина
В браузере открыт учебный магазин по адресу http://195.239.174.35. Страница содержит форму поиска и таблицу товаров с названием, типом, описанием и ценой. Поле поиска служит точкой ввода пользовательских данных; в последующих запросах ему соответствует GET-параметр product. Само наличие формы ещё не доказывает уязвимость: подтверждение получено на следующих этапах.
Определён интерфейс для проверки обработки поисковых запросов.

Рисунок 2 - Веб-интерфейс магазина
3.3 Проверка параметра product
Для проверки поискового параметра запущен sqlmap. Режим batch использует стандартные ответы на вопросы программы, а flush-session очищает сохранённые результаты предыдущей проверки. Программа предупреждает о пустом значении product, проверяет соединение и стабильность страницы. На этом снимке показано начало анализа; последующие результаты подтверждают доступ к данным через SQL-инъекцию.
sqlmap http://195.239.174.35/?product= --batch --flush-session
На фоне виден результат сетевого обследования: Apache 2.4.54 (Debian) и MariaDB 11.5.2. Позднее sqlmap определяет UNION-инъекцию с пятью столбцами.

Рисунок 3 - Проверка параметра product
3.4 Получение списка баз данных
В выводе sqlmap перечислены шесть имён: information_schema, mysql, website, sys, performance_schema и #mysql50#.local. Для дальнейшего исследования выбрана прикладная база website. Служебные базы также оказались видимыми через уязвимый параметр. Во время извлечения sqlmap сообщает о затруднениях с полным UNION-методом и переходе к частичному извлечению.
Список баз данных получен.

Рисунок 4 - Получение списка баз данных
3.5 Запрос таблицы с первым флагом
В терминале подготовлена команда выгрузки таблицы flag из базы website. Параметр D задаёт базу данных, T задаёт таблицу, а dump запрашивает её содержимое. Этот этап направлен на получение контрольного значения первого задания через выявленную SQL-инъекцию.
sqlmap http://195.239.174.35/?product= --batch --flush-session -D website -T flag --dump
Выбрана таблица website.flag. Результат её чтения показан на следующем снимке.

Рисунок 5 - Запрос таблицы с первым флагом
3.6 Извлечение хеша первого флага
Sqlmap вывел одну запись таблицы website.flag. Столбец hash_flag_in_mysql содержит значение f2986f60b7d35cf72fb8b7815d120359. Программа также сообщает о сохранении выгрузки в файл flag.csv. Далее открыта справка Hashcat командой hashcat -h для подготовки проверки хеша.
f2986f60b7d35cf72fb8b7815d120359 Получен хеш контрольного значения. Сообщение sqlmap об отсутствии найденного открытого текста относится к его собственной проверке, а не к последующему результату Hashcat.

Рисунок 6 - Извлечение хеша первого флага
3.7 Восстановление первого флага
Hashcat завершил проверку со статусом Cracked. В выводе указаны режим 0 (MD5), словарь /usr/share/wordlists/rockyou.txt и одна восстановленная запись из одной. Строка результата связывает извлечённый хеш со значением 86054. Это подбор исходного значения по словарю и сравнению хешей, а не расшифрование MD5.
f2986f60b7d35cf72fb8b7815d120359:86054 Первый флаг: 86054.

Рисунок 7 - Восстановление первого флага
3.8 Проверка таблицы flag в системной базе
После получения первого флага предпринята попытка запросить таблицу flag уже из базы mysql. На снимке видна подготовленная команда с изменённым именем базы.
sqlmap http://195.239.174.35/?product= --batch --flush-session -D mysql -T flag --dump
Начата проверка другого расположения данных. Успешная выгрузка mysql.flag зафиксирована.

Рисунок 8 - Проверка таблицы flag в системной базе
3.9 Ошибка выбора таблицы и изменение запроса
Sqlmap смог получить имена столбцов таблицы flag в базе mysql. Затем в командной строке таблица заменена на user. В верхней части вывода указан тип SQL-инъекции MySQL UNION query (NULL), 5 columns; также определены Linux Debian, PHP 7.4.33 и Apache 2.4.54.
sqlmap http://195.239.174.35/?product= --batch --flush-session -D mysql -T user --dump

Рисунок 9 - Ошибка выбора таблицы и изменение запроса
3.10 Прямое подключение к MariaDB
Sqlmap сообщает о сохранении выгрузки mysql.user в user.csv. Затем выполнено прямое подключение клиентом mysql к узлу 195.239.174.35 на порт 3306 под учётной записью root. Сервер принимает подключение и выводит приглашение MariaDB. Команда на снимке содержит пароль учебного стенда;
Подтверждён прямой доступ к СУБД под root. Это учётная запись базы данных; данный факт сам по себе означает получение root-доступа к операционной системе.

Рисунок 10 - Прямое подключение к MariaDB
3.11 Проверка привилегии FILE
Выполнен запрос к mysql.user для проверки файловой привилегии учётной записи root с Host, равным %. Сервер вернул File_priv = Y. Тем самым подтверждено наличие привилегии FILE у проверенной записи. Возможность прочитать конкретный файл проверяется следующим запросом.
SELECT File_priv FROM mysql.user
WHERE User = 'root' AND Host = '%';
Проверка вернула одну строку со значением Y.

Рисунок 11 - Проверка привилегии FILE
3.12 Чтение файла и получение второго флага
Через функцию LOAD_FILE запрошен файл /var/lib/mysql/flag в файловой системе сервера СУБД. Первые две попытки не завершались точкой с запятой: клиент ожидал продолжения ввода, после чего запрос отменялся. Завершённый запрос выполнился и вернул контрольное значение 14927.
SELECT LOAD_FILE('/var/lib/mysql/flag');
Второй флаг: 14927. Подтверждено чтение серверного файла средствами SQL; запуск команд ОС этим снимком подтверждается.

Рисунок 12 - Чтение файла и получение второго флага
3.13 Переход к заданию о Docker
После выхода из клиента MariaDB работа продолжена в оболочке reduser2@kali. Попытка чтения /root/flag возвращает Permission denied, а чтение с sudo сообщает об отсутствии файла. Файл /output также не найден. Затем введена команда подготовки каталога /tmp/cgrp и монтирования cgroup с контроллером rdma.
Начата попытка задания «Побег из Docker». Переход в оболочку контейнера целевого сервера в материалах показан; видимое приглашение остаётся reduser2@kali.

Рисунок 13 - Переход к заданию о Docker
3.14 Ошибки определения пути файловой системы
На следующем этапе выполнялись попытки извлечь путь из /etc/mtab с помощью sed и записать путь к скрипту в release_agent. Несколько запусков завершились ошибкой unterminated s command. После изменения синтаксиса команда вывела /cmd. Такое значение согласуется с пустым префиксом host_path; корректный путь файловой системы хоста этим выводом не подтверждён. Далее создана начальная строка скрипта /cmd.
Зафиксированы ошибки синтаксиса sed и отсутствие подтверждения корректного определения host_path.

Рисунок 14 - Ошибки определения пути файловой системы
3.15 Подготовка скрипта чтения флага
В файл /cmd добавлялась команда чтения /root/flag с перенаправлением результата в output по пути, зависящему от host_path. Замысел попытки состоял в запуске этого скрипта через release_agent. Скриншот подтверждает ввод команд подготовки файла.
Подготовлен очередной этап попытки выхода из контейнера. Успешное пересечение границы изоляции зафиксировано.

Рисунок 15 - Подготовка скрипта чтения флага
3.16 Ошибка обращения к cgroup.procs
Скрипту /cmd назначены права на выполнение. Затем предпринята попытка записи идентификатора процесса в /tmp/cgrp/x/cgroup.procs. Оболочка вернула сообщение Directory nonexistent.
sh: 1: cannot create /tmp/cgrp/x/cgroup.procs: Directory nonexistent
Показанная попытка привела к подтверждённому получению флага.

Рисунок 16 - Ошибка обращения к cgroup.procs

На последнем терминальном снимке видны повторная настройка notify_on_release, запись release_agent, подготовка /cmd и обращение к cgroup.procs.
sudo cat /output

4 Анализ результатов
Первое задание показало возможность чтения данных базы website через параметр product. Из таблицы flag извлечён MD5-хеш, для которого Hashcat нашёл значение 86054. Это подтверждает нарушение конфиденциальности данных веб-приложения.
Во втором задании установлено прямое соединение с MariaDB под root. Проверка File_priv дала Y, а LOAD_FILE вернула из /var/lib/mysql/flag значение 14927. Таким образом, доступ к СУБД позволил читать файл на стороне сервера. Получение системной оболочки через СУБД в представленных материалах не зафиксировано.
В третьем задании показана попытка использования cgroup и release_agent, сопровождавшаяся ошибками sed и обращения к cgroup.procs. Последняя проверка /output вывела флаг. Видимые команды выполнялись в оболочке reduser2@kali;
5 Обнаружение и меры защиты
Скриншоты содержат журналы IDS, аудита СУБД или веб-сервера. Ниже приведены рекомендуемые направления контроля и защиты; их внедрение и проверка в ходе этой работы не зафиксированы.
Для веб-приложения следует использовать параметризованные запросы и ограничить права его учётной записи в СУБД необходимыми операциями. При разборе инцидента полезно сопоставить журнал HTTP-запросов к параметру product с журналами базы данных. Доступ приложения к системным таблицам пользователей следует исключить.
Для СУБД следует ограничить сетевую доступность порта 3306, запретить ненужные удалённые подключения административных учётных записей и заменить слабые пароли. Привилегия FILE должна предоставляться только при обоснованной необходимости. Также следует ограничивать доступ процесса СУБД к файлам средствами операционной системы. Для хранения пользовательских паролей необходим специализированный алгоритм хеширования с солью; простой MD5 для этой цели не подходит.
Для контейнерной среды следует проверить избыточные привилегии, доступ к cgroup и доступные монтирования файловой системы хоста. Контейнеры следует запускать с минимально необходимыми правами, использовать ограничения AppArmor или SELinux и seccomp. Наличие уязвимой конфигурации Docker в этой работе не доказано, поэтому данные меры рассматриваются как рекомендации по проверке и укреплению изоляции.
