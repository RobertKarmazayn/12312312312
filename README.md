Лабораторная работа № 1. Расследование инцидента в Ampire

**Тема:** расследование утечки конфиденциальной информации о местоположении сотрудников и ограничение доступа к серверу SS7 средствами pfSense и iptables.

**Выполнил:** Кармазян Роберт, Кузьмин Артем, Бутерин Арсений, Джало Дмитрий 
**Группа:** НБИбд-01-23 (Дельта) 
**Дата 30.09

## 1. Цель работы

Изучить учебный сценарий эксплуатации Any Time Interrogation (ATI) в инфраструктуре Ampire, рассмотреть предусмотренные методикой способы обнаружения запросов и настроить фильтрацию SCTP-трафика от узла нарушителя на межсетевом экране и сервере.

## 2. Исходные данные

Работа основана на методическом документе «ЛР1 Delta (1) (2).pdf», сценарий «Расследование инцидента с утечкой конфиденциальной информации о местоположении сотрудников», и доступных скриншотах выполнения.

| Компонент | Назначение или значение |
| --- | --- |
| Ampire | Учебная среда моделирования инцидента |
| Kali Linux | Внешний узел нарушителя по методике |
| DragonOS | Сервер, эмулирующий взаимодействие SS7 |
| SigPloit | Средство моделирования сценария в методике |
| pfSense | Межсетевой экран, веб-интерфейс `https://10.10.1.254` |
| Узел нарушителя | `195.239.174.11` |
| Защищаемый узел в pfSense | Псевдоним `Telecom` |
| Адрес SSH-подключения к DragonOS | `10.10.1.36` |
| Фильтруемый протокол | SCTP |
| Порт сервиса в правиле iptables | `2906` |

В исходном сообщении указаны 11 скриншотов, однако из вложений доступны 9 файлов. Они включены в отчет. Для двух недоступных изображений в приложении оставлены места без предположений об их содержимом.

## 3. Краткое описание инцидента и способа обнаружения

Согласно разделам 3–5 методики, внешний нарушитель обнаруживает сервис на порту `2906` в сети `195.239.174.0/24` и использует запросы ATI для получения конфиденциальных сведений об абонентах. В учебной среде взаимодействие моделируется средствами SigPloit.

Методика предусматривает исследование журнала:

```text
/home/gh0/restcomm-jss7-7.0.1383/ss7/maplog.log
```

Также предлагается найти дамп трафика в `/var/log` и открыть его в Wireshark, чтобы сопоставить запросы ATI и ответы сервера. Эти действия описывают порядок расследования по заданию. Доступные отдельные скриншоты не показывают содержимое `maplog.log` или разбор ATI, поэтому факт выполнения этой части и конкретные полученные сведения об абонентах по ним не подтверждаются.

## 5. Настройка фильтрации на DragonOS

### 5.1. Подключение к серверу

Выполнено SSH-подключение к серверу DragonOS:

```bash
ssh user@10.10.1.36
```

На снимке видны приветствие DragonOS и приглашение оболочки `user@user-virtual-machine:~$`, подтверждающие успешный вход. Окно Wireshark на заднем плане показывает захват трафика, но не подтверждает анализ конкретных запросов ATI.

![Успешное SSH-подключение к DragonOS по адресу 10.10.1.36](image/07-dragonos-ssh.jpg)

*Рисунок 7 — Подключение к консоли защищаемого сервера.*

### 5.2. Добавление правила iptables

В консоли введена команда, показанная на скриншоте:

```bash
sudo iptables -A INPUT -s 195.239.174.11 -p sctp -m sctp --dport 2906 -j DROP
```

| Параметр | Назначение |
| --- | --- |
| `-A INPUT` | Добавление правила в конец цепочки входящих пакетов, адресованных этому узлу |
| `-s 195.239.174.11` | Проверка адреса источника |
| `-p sctp -m sctp` | Выбор SCTP и его модуля сопоставления |
| `--dport 2906` | Проверка порта назначения |
| `-j DROP` | Отбрасывание соответствующих пакетов |

![Выполнение команды iptables для блокировки входящего SCTP-трафика от 195.239.174.11 на порт 2906](image/08-iptables-drop.jpg)

*Рисунок 8 — Добавление локального правила фильтрации на сервере.*

Команда относится к цепочке `INPUT`. Хотя вводный текст раздела 6.2 методики упоминает входящий и исходящий трафик, приведенная команда не добавляет отдельного правила в `OUTPUT` и не является самостоятельной настройкой блокировки обоих направлений.

### 5.3. Просмотр текущих правил

Для вывода конфигурации выполнена команда:

```bash
sudo iptables-save
```

В выводе таблицы `filter` присутствует правило:

```text
-A INPUT -s 195.239.174.11/32 -p sctp -m sctp --dport 2906 -j DROP
```

![Вывод iptables-save с правилами DROP для SCTP от 195.239.174.11 на порт 2906](image/09-iptables-rules.jpg)

*Рисунок 9 — Подтверждение наличия правила в текущей конфигурации iptables.*

На снимке видны четыре одинаковые записи `DROP`. Это указывает на повторное добавление одного и того же правила; для описанного условия достаточно одной записи. Политики цепочек `INPUT`, `FORWARD` и `OUTPUT` показаны как `ACCEPT`.

Показанный запуск `iptables-save` выводит конфигурацию в терминал. Перенаправление в файл и настройка автоматического восстановления правил не представлены, поэтому сохранение фильтрации после перезагрузки не подтверждено.

## 6. Результаты

| Этап | Подтвержденный результат |
| --- | --- |
| Настройка pfSense | Добавлено блокирующее правило IPv4 SCTP от `195.239.174.11` к `Telecom`; интерфейс сообщает об успешном применении изменений |
| Подключение к DragonOS | Выполнен успешный вход по SSH на `10.10.1.36` |
| Настройка iptables | В текущей конфигурации присутствует `DROP` для входящего SCTP-трафика от `195.239.174.11` на порт `2906` |
| Анализ журнала и запросов ATI | Порядок приведен в методике; доступными скриншотами выполнение не подтверждено |
| Повторная проверка доступа после настройки | Результат в доступных материалах отсутствует |
| Восстановление iptables после перезагрузки | Не подтверждено |

Для завершения проверки эффективности требуется зафиксировать результат повторной попытки обращения к сервису в учебной среде и сопоставить его с журналом или счетчиками фильтра. Если необходимо проверить каждый уровень защиты отдельно, результаты pfSense и локального фильтра следует рассматривать отдельно: блокировка на pfSense может не допустить пакеты до сервера.

## 7. Вывод

В ходе работы рассмотрен сценарий утечки сведений об абонентах через ATI и настроены два уровня ограничения доступа: правило SCTP на pfSense и правило для порта `2906` в iptables на сервере DragonOS. Доступные скриншоты подтверждают применение конфигурации pfSense и наличие локальных правил фильтрации. Для вывода о фактическом прекращении нежелательного доступа необходим результат контрольной проверки. Настроенные ограничения относятся к указанному источнику и не подтверждают устранение всех возможных способов эксплуатации SS7.
